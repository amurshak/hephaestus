**Codex spawn form verified against a live CLI** (#139): the `/worktrees` Step 6 spawn block that `scripts/sync-codex-adapters.sh` emits — `codex "/start-issue <N>"` — rested on the documented `codex [OPTIONS] [PROMPT]` signature, never on observed behavior, because the local binary was unrunnable. Confirmed against codex-cli 0.145.0: a bare positional prompt opens the interactive TUI and auto-submits, a leading-slash prompt is passed through as literal text rather than intercepted as a TUI command, and Codex matches it to the generated skill implicitly via the `Use for /<name> requests.` description anchor — verified with the skill in both `$CODEX_HOME/skills` (user install) and a project's `.agents/skills` (project install, which Codex does read). A spawned git worktree also inherits the parent repo's trust, so no per-directory trust dialog blocks the seeded prompt and no Codex analogue of Claude's `--permission-mode default` is needed. Both claims held, so no generator change was required. New `scripts/verify-codex-load.sh` (sibling of the OpenCode and Hermes verifiers: skips when the CLI is absent, `--require` to fail) guards the assumption going forward — it asserts `codex --help` still documents the positional `[PROMPT]`, then checks the generated skills and agent roles against whichever root actually holds them, since a `--project` install scaffolds only `.agents/skills/orient` and leaves the shared set in `$CODEX_HOME`. Wired into CI alongside the OpenCode live check, and covered hermetically in `tests/test_codex_adapters.sh` by a stub CLI so the assertions do not depend on whether a contributor has Codex installed.
