**`verify-hermes-load.sh` no longer reports healthy on an ambiguous skill** (#155): the preload check tested only that `hephaestus/start-issue` existed in the project's own skills dir, so it printed `✓ Hermes loads hephaestus skills and delegate briefs` while `/worktrees` was broken. Hermes resolves `hermes chat -s hephaestus/start-issue` via `skill_view`, which refuses to guess when more than one candidate matches and returns `success: false` — the CLI then aborts with `Unknown skill(s)`, killing every spawned window. Two claimants are as fatal as none, and the state is reachable from the README's own instructions: a user-level install symlinks `~/.hermes/skills/hephaestus/*` into the clone while `--vendor` writes real copies that a project then names in `skills.external_dirs`. The check now enumerates every root Hermes searches — its home skills dir plus each `external_dirs` entry, both the block and inline YAML list forms, since under-counting would restore the very false-healthy report the check exists to prevent — and fails when more than one distinct skill claims the identifier, naming each colliding path so the user knows which install to drop. Dedup is by resolved path, matching Hermes: a symlink and its target count once, so a correctly wired machine is not flagged. Regression tests cover the ambiguous case, the symlinked-dedup case, and the inline list. The existing verifier tests now sandbox `HOME` and drop any inherited `HERMES_HOME` — with `~/.hermes/skills` newly in scope, their result would otherwise depend on whether the developer running the suite happens to have a user-level install.
