**`test_loop.sh` no longer races a wall-clock constant** (#162): five call sites started `loop.sh` in the background and then waited a fixed `sleep 1` (or `sleep 0.5`) before asserting on the lockfile, banner, or mock invocation. Under load the background process had not reached lock creation within that second, so the "creates lockfile and writes PID" group failed 2–3 assertions intermittently — a spurious red suite during `/ship`, which forces exactly the is-this-a-regression judgement call automation should not have to make. New `wait_for <timeout> '<condition>'` helper in `tests/helpers.sh` polls at 100ms up to a bound and returns non-zero on timeout, leaving the following assertion to report the failure so assertion counts stay stable. Each site now waits on the state it actually depends on rather than on elapsed time: a non-empty `$LOCK_DIR/pid` (which `loop.sh` writes immediately after taking the lock, so it covers the directory, the pid file, and its contents together), the banner's last `Stop     : kill` line, a non-empty mock args file, and — for teardown — the lock's *absence*. The first test also now clears a stale lock before launching, as the other three already did; without that, a leftover lock makes `loop.sh` exit 1 and the pid file never appears at all. Verified deterministically rather than by re-running and hoping: shimming a slow `shasum` onto `loop.sh`'s PATH delays lock creation past the old one-second window, which reproduces the reported failure verbatim under the old pattern and passes under the new one.
