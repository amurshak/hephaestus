**Cursor `/worktrees` spawned sessions that never ran the command** (#156): the Step 6 spawn form `cursor-agent "/start-issue <N>"` claimed the positional prompt seeded the session with the command. Measured against a live cursor-agent 2026.07.23-e383d2b, half of that was wrong — the same shape of unverified assumption that made #143 real. A positional prompt *does* open an interactive session, but Cursor's slash dispatcher is bound to the TUI input widget, so `/start-issue <N>` was never dispatched: it reached the model as literal text. In an identical workspace the command resolved from context with zero tool calls when passed under `-p` or typed into the input, while the positional form sent the model globbing the worktree for a file matching the command name. For the default user-level install the failure is total — the command lives in `~/.cursor/commands`, outside the worktree, so the search finds nothing and the spawned session never starts the issue. Step 6 now spawns `cursor-agent -p "/start-issue <N>"`, which dispatches from `.cursor/commands` and `~/.cursor/commands` alike, and the generator localizes the spawn per command rather than rewriting any `claude "<prompt>"` — a generic rule would quietly turn a new Claude-form spawn into text the model never acts on, so an unmatched one now trips the drift check instead. New `scripts/verify-cursor-load.sh` guards both halves of the contract against a live CLI — the positional prompt and `-p` — and checks the generated commands, subagents, and `hephaestus.mdc` sit in a root Cursor reads, probing for our rule by name so a project's own `.mdc` files never claim it. CI installs the CLI from the vendor script — it is not on npm, where that package name belongs to an unrelated third party — and runs the check with `--require`, so a Cursor release that drops either flag fails the build instead of skipping quietly. The script's own logic is covered hermetically by a stub CLI in `tests/test_cursor_adapters.sh`, so contributors without Cursor still exercise it.
